# 아키텍처 마이그레이션 계획

## 현재 상태

이 문서를 작성하는 시점 기준으로 **코드는 아직 마이그레이션되지 않았습니다.** 현재 코드베이스는 `CLAUDE.md`에 설명된 기존 Vite + Express + SQLite + 로컬 디스크 구조 그대로입니다. 이 문서는 다음 작업을 위해 확정한 방향과, 아직 트리거되지 않은 후속 마이그레이션 계획을 기록합니다.

## 배경과 목표

- 지금은 개인용, 포토앨범 느낌의 위시리스트로 여러 기기에서 동기화해서 사용
- 추후 여러 사용자에게 공개하는 서비스로 확장할 가능성을 염두에 두고 아키텍처를 다시 검토함
- 다만 확장 가능성 때문에 처음부터 복잡한 멀티벤더 인프라를 짓지는 않기로 함 — "지금 당장 할 것"과 "나중에 실제 신호가 오면 바꿀 것"을 분리해서 결정

## 1단계 (다음 작업): Next.js + Supabase로 전환

- **프레임워크**: Vite SPA + Express → **Next.js(App Router)** 로 통합. 이유는 SEO가 아니라 프론트/백엔드 배포 통합, 타입 공유, `next/image`를 통한 이미지 최적화 때문.
- **DB / Storage / Auth**: 전부 **Supabase**(Postgres + Storage + Auth)로 시작. Neon/R2/Auth.js처럼 영역별로 벤더를 나누지 않고, 올인원으로 빠르게 구현하는 것을 우선함.
- **스키마**: `products` / `categories`에 `user_id` 컬럼을 처음부터 포함할 것. Supabase Auth를 1일차부터 쓰면 자연스럽게 따라옴 — 지금은 유저가 나 하나뿐이어도, 나중에 소급 적용하는 것보다 처음부터 있는 편이 훨씬 저렴함.
- **이미지 처리**: **1일차부터 리사이즈/압축을 넣지 않는다.** 원본 그대로 저장하고, 실제 용량이 얼마나 쌓이는지 눈으로 본 뒤 필요해지면 그때 sharp로 리사이즈/압축을 도입 — 개인용 앱 규모에서 미리 만들 이유가 약함(2단계 모니터링 기준과 동일한 "트리거가 오면 대응" 원칙 적용).
  - **트레이드오프**: 리사이즈를 늦게 도입하면 신규 업로드에만 적용되고, 그 시점까지 쌓인 원본들은 자동으로 줄어들지 않음 — 도입 시점에 기존 이미지 일괄 재처리(백필) 스크립트가 별도로 필요할 수 있다는 점을 감안할 것.
  - **Vercel Image Optimization 관련 (별도 축, 잊지 말 것)**: `next/image`를 쓰면 Vercel이 이미지를 자동으로 리사이즈/최적화하는데, 이 무료 한도는 **저장 용량이 아니라 "처리(변환)한 고유 이미지 개수"** 기준(월 1,000장 수준)이다. 즉 원본을 압축하지 않고 그대로 두더라도, `next/image`가 매번 다른 사이즈로 이 원본을 변환하면 용량과 무관하게 이 한도를 먼저 소진할 수 있음. 리사이즈/압축 도입 여부와 별개로, 업로드 개수가 늘어나면 이 한도도 함께 모니터링해야 하며, 필요 시 런타임 최적화를 끄고 업로드 시점에 사이즈별(썸네일/원본)로 미리 만들어 저장하는 방식으로 전환해 이 비용 축 자체를 없앨 수 있음.
- **호스팅**: Vercel로 시작. 단 Vercel 전용 서비스(Vercel Postgres, Vercel Blob)는 쓰지 않고 Supabase를 그대로 사용 — 나중에 다른 호스팅으로 옮길 때 마찰을 줄이기 위함.

## 2단계 (트리거 발생 시): 사용량 기반 단계적 마이그레이션

Supabase 무료 티어 세 항목 중 **DB 용량(약 500MB)과 Auth MAU(약 5만 명)는 이 프로젝트 규모에서 사실상 문제 되지 않음.** 실제 병목은 **스토리지(약 1GB)와 이그레스(월 대역폭, 약 5GB)** 이며, 스크린샷 압축·평균 세션당 조회량 기준으로 **활성 유저 약 50~100명** 선에서 소진될 것으로 추정.

**모니터링 기준**: Supabase 대시보드에서 스토리지/이그레스 사용량이 **70~80%에 도달하면 마이그레이션 착수.** 100%까지 다 채우고 대응하면 급하게 처리해야 하므로 미리 여유를 둘 것.

**마이그레이션 순서** (쉬움 → 어려움, 한도에 먼저 근접한 항목부터 우선):

1. **DB → Neon** — 표준 Postgres끼리라 `pg_dump`/`pg_restore`로 이전하고 연결 문자열만 교체. 셋 중 가장 쉽고 리스크가 낮음.
2. **Storage → Cloudflare R2** — 둘 다 S3 호환. 객체 일괄 복사(rclone 등) + DB에 저장된 URL 생성 로직 갱신. 이미지 변환은 업로드 시 압축 + `next/image`로 대체하고, 비공개 접근 제어는 S3 SDK의 presigned URL을 직접 구현.
3. **Auth → Auth.js** — 가장 어려움. 기술적으로는 가능하나 비밀번호 해시 포맷 차이로 전 유저가 재로그인/비밀번호 재설정을 해야 함. **Auth만 계속 Supabase에 남기는 하이브리드(Neon + R2 + Supabase Auth)도 그 자체로 유효한 최종 상태** — 이 단계를 안 하는 게 실패가 아니라 정당한 선택지임.

**중요**: 이 순서와 시점은 "언젠가 유저가 많아지면"이 아니라 위 모니터링 기준(70~80% 사용량)이 실제 트리거. 미리 예방적으로 옮기지 않고, 지금은 개발 속도를 우선함.

## 캐싱 관련 주의사항 (2단계 이후 해당)

비공개 이미지를 서명 URL(presigned/signed URL)로 서빙하면, URL 자체가 요청마다 바뀌어 브라우저/CDN 캐시의 캐시 키가 매번 달라지고 캐싱 효과가 사라짐(매번 캐시 미스). 서명 URL의 만료시간을 의도적으로 길게(예: 1일~1주) 설정해야 그 기간 동안 캐싱이 실제로 작동함 — 보안(짧은 만료)과 캐시 효율(긴 만료) 사이의 트레이드오프를 의식적으로 선택해서 설계할 것.

## 향후 기능: AI OCR (스크린샷에서 제품명/가격 등 자동 추출)

- 위 마이그레이션 계획과 **독립적인 기능** — 도입 시점이나 DB/Storage/Auth 벤더 선택에 영향을 주지 않음
- AI 비전 API(Claude, GPT 등) 비용은 Supabase/Neon/R2와 완전히 별개의 축이므로 **따로 모니터링** 필요 (대체로 가입 시 소량의 무료 크레딧만 있고 이후 종량 과금)
- 비용이 조회 빈도가 아니라 **업로드(추가) 빈도에 비례**해서, 이그레스 문제보다 훨씬 예측 가능하고 규모도 작음
- 아무 때나 추가 가능하며, 지금 아키텍처 결정에 영향을 주지 않음

## 검토했지만 채택하지 않은 것 (요약)

- **처음부터 Neon + R2 + Auth.js로 가지 않은 이유**: 솔로 개발 단계에서 서비스 4곳을 각각 세팅/연동하는 비용이 큼. 이미 이 조합으로의 마이그레이션 경로가 안전하다는 걸 확인했으므로, 지금은 개발 속도를 우선하고 실제 트리거가 왔을 때 옮기는 편이 합리적이라고 판단.
