# Phase 17 — 가격 정확도 개선(B1): 중고거래 가격 규칙과 좋아요 수 오추출

> **이 문서 사용법**: Claude Code에 이 파일 전체를 컨텍스트로 넘기고 "**Step N을 진행해달라**"고 한 Step씩 요청한다. **사람** Step(API 측정 실행·SQL·함수 배포·실기기 확인)은 에이전트가 대신하지 않는다. 에이전트는 `ANTHROPIC_API_KEY`를 다루지 않는다. Step마다 변경 요약을 보고하고 **승인을 받은 뒤 커밋**한다. PR은 모든 에이전트 Step이 끝난 뒤 승인받고 올린다. 커밋 메시지에 Phase·Step 번호를 넣지 않는다.
>
> **브랜치**: 최신 `dev`에서 분기한 `feat/phase-17-price-accuracy`. worktree `../wish-shot-eval`에서 작업한다. 정답셋 데이터(git 제외)가 이 폴더에만 있기 때문이다. 이 폴더는 Phase 13이 끝난 뒤 머지된 `feat/phase-13-goldset-eval`에 머물러 있으므로, 세션 시작 시 `git fetch` → `git status --short --branch`로 확인하고 `origin/dev`에서 새 브랜치를 만든다.
>
> **바뀌는 것**: `prompt.ts`의 가격 규칙(중고거래 문단, 조건부로 좋아요 수 보강), `samples/`(회귀 케이스 1개, 측정 기록), 문서. Step 5를 코드로 하기로 정한 경우에만 `index.ts`의 출력 후처리. **Edge Function 재배포(사람)**. 앱 재빌드·OTA 없음.
>
> **레인 경계(중요)**
> - `supabase/migrations/**`, `src/**`, `app.json`은 건드리지 않는다.
> - `supabase/functions/parse-screenshot-text/index.ts`는 Phase 15(요청 제한, `../wish-shot-sec`)가 고친다. 이 Phase는 **Step 5를 코드로 하기로 정한 경우에만**, Phase 15가 `dev`에 머지된 뒤 이 브랜치에 `dev`를 반영하고 나서 고친다. 그 전에는 건드리지 않는다.
> - 출력 스키마, 모델(`MODEL`), `TEMPERATURE`는 바꾸지 않는다. 모델 교체는 별도 판단이다(REPORT '다음 개선 후보').
> - **배포 순서**: Phase 15와 같은 함수(`parse-screenshot-text`)를 배포한다. `supabase functions deploy`는 내 폴더의 코드를 통째로 올린다. 나중에 배포한 쪽에 다른 쪽 변경이 없으면 먼저 배포한 변경이 사라진다. 그래서 **두 변경이 모두 들어간 코드(`dev` 머지 후)에서만 배포한다**(Step 8).
>
> **정답셋 규칙(Phase 13에서 이어짐)**
> - 원문(`goldset/data/`)·결과(`goldset/out/`)는 git 제외다. 원문·모델 출력(상품명 등)은 채팅에 출력하지 않는다(개수·유형만).
> - **`goldset/out/results.csv`·`summary.md`(Phase 13 기준선)는 덮어쓰지 않는다.** 기준선 비교와 Phase 21(구매처 찾기)의 입력으로 쓴다. 새 결과는 `--out`으로 **`goldset/out/` 아래 하위 폴더**에 쓴다. `out/` 밖에 만들면 git 제외가 적용되지 않는다.
> - **홀드아웃**: 고치는 동안은 `--exclude-holdout`(공개 33장)으로만 잰다. 홀드아웃 11장은 **최종 프롬프트로 한 번만**(Step 6) 재고 정답 수만 적는다. 실패 내용은 보지 않고, 홀드아웃 결과를 보고 다시 고치지 않는다.
> - 정답셋은 고치거나 추가하지 않는다(v1 고정).
>
> **한 번에 하나**: 중고 규칙(Step 3~4)을 먼저 바꾸고 측정을 끝낸다. 좋아요 수 수정(Step 5)은 그 뒤 따로 바꾸고 따로 잰다. 두 효과를 나눠 보기 위해서다.

> **숫자 쓰는 규칙**: 'N장 중 M장'으로 쓴다. 통계적 유의성은 주장하지 않는다. 비교는 '한쪽만 맞힌 장'(앞쪽만 : 뒤쪽만)으로 적고, 표본이 작다는 주의를 함께 적는다.

## Step 2 — 좋아요 수 재현 시험 (에이전트 → 사람)

배경
- 10/20 오추출 방지 규칙을 배포한 **뒤**, 실기기의 릴스 화면 하나에서 쉼표 붙은 좋아요 수("1,817")가 가격으로 두 번 뽑혔다. 그 규칙은 PR #28로 들어갔다: '좋아요·조회 수는 가격이 아님', '원·가격 라벨·할인율 근거가 있을 때만 가격'.
- 그 뒤 프롬프트는 바뀌지 않았다. **지금 프롬프트가 바로 그 실수를 한 프롬프트다.** 규칙이 이미 있는데 모델이 그 화면에서 지키지 않은 것이다.
- 릴스는 아이콘 옆에 숫자만 있어 OCR 원문에 '좋아요' 글자가 없었을 가능성이 크다. 추정이다(그 화면의 원문은 확인하지 않았다).
- 기존 케이스 2(라벨 없는 작은 수)와 6(라벨 붙은 쉼표 수)은 이 모양을 다루지 않는다.
- 정답셋(같은 프롬프트)에서는 라벨 없는 쉼표 숫자가 있는 공개 화면이 9장이다(SNS류 B·C 5장).
  - 운영이 그런 숫자를 가격으로 잘못 낸 장은 0장이다.
  - 그런 숫자를 가격으로 낸 1장은 정답 가격이었다. 진짜 가격도 라벨 없이 나올 수 있다는 뜻이다. 단순한 서버 측 검증이 맞는 가격을 지우는 이유다.
- 즉 이 실수는 드물지만 아직 남아 있을 수 있다. 고치는 방법은 **먼저 재현되는 시험 사례가 있어야** 따질 수 있다. 이 Step이 그 재현 시험이다.

1. (에이전트) `samples.md`에 케이스 8을, `eval.ts`의 `CASES`에 같은 케이스를 더한다.
   - **가상 원문**: 릴스·피드 화면. 아이콘 옆 **라벨 없는 쉼표 숫자**(네 자리 좋아요·댓글 수)가 있고, `원`도 가격도 없다. 실제 화면 문구는 옮기지 않는다.
   - 기대: `{ "price": null }`.
2. (사람) **바꾸기 전 프롬프트로** `eval.ts 3`을 실행한다. 키 설정은 `samples.md` '자동 검증' 절의 방식을 따른다.
   - **케이스 8이 FAIL(재현됨)**: 문제가 지금 프롬프트에 남아 있다는 증거다. 이 케이스가 Step 5의 시험 사례가 된다. Step 4 회귀 조건에서는 케이스 8을 빼고 결과만 기록한다.
   - **케이스 8이 PASS(재현 안 됨)**: 3번으로 실제 기록 재현을 시도한다.
3. **실제 기록으로 재현 시도** (사람 결정 2026-11-06 — 케이스 8이 PASS일 때만)
   - 10/20 실기기 테스트는 개발자 본인 계정 기록이므로 `ops.internal_users` 규칙 안에서 찾는다. 로그는 저장한 경우에만 남는다.
   - (사람) SQL Editor에서 **개수만** 먼저 확인한다. 원문은 출력하지 않는다.
     ```sql
     select count(*) as n, min(l.created_at) as first_at, max(l.created_at) as last_at
     from public.analysis_logs l
     where l.user_id in (select user_id from ops.internal_users)
       and l.created_at >= '2026-10-20 00:00:00+09' and l.created_at < '2026-10-22 00:00:00+09'
       and (l.parsed->>'price') = '1817';
     ```
     - 0건이면 그 화면은 저장되지 않은 것이다. "실제 기록 없음"으로 기록한다.
   - 1건 이상이면 (사람) `select l.id, l.raw_text`로 같은 조건의 행을 CSV로 받아 `samples/goldset/data/repro/raw.csv`에 둔다(git 제외 폴더).
   - (에이전트) 같은 폴더에 `labels.csv`를 만든다. 내용은 사람이 확인한 정답(`type` C, `price_gold` null)이다. dry-run으로 형식을 검증한다. 원문은 출력하지 않는다.
   - (사람) 바꾸기 전 프롬프트로 실행한다.
     ```
     deno run --allow-net=api.anthropic.com --allow-env=ANTHROPIC_API_KEY --allow-read=supabase/functions/parse-screenshot-text/samples --allow-write=supabase/functions/parse-screenshot-text/samples/goldset/out supabase/functions/parse-screenshot-text/samples/goldset-eval.ts --runs 3 --variants v1 --data supabase/functions/parse-screenshot-text/samples/goldset/data/repro --out supabase/functions/parse-screenshot-text/samples/goldset/out/repro
     ```
   - 3회 중 2회 이상 숫자를 내면 재현된 것이다. 이 비공개 재현 사례가 Step 5의 시험 사례가 된다. 커밋하는 케이스 8은 계속 가짜 원문이다.
   - 원문에는 다른 사람의 계정명이 섞일 수 있다. 채팅 출력 금지와 커밋 금지는 정답셋과 같다.
4. 가짜 원문과 실제 기록 모두 재현되지 않으면 "재현 0"으로 기록한다. 케이스 8은 회귀 감시용으로만 두고, Step 5는 건너뛴다.

**DoD**: 케이스 1~8 결과와 실제 기록 재현 결과(해당할 때)를 기록 → 보고 → 승인 → 커밋.

## Step 3 — 중고거래 가격 규칙 (에이전트)

1. `prompt.ts` `SYSTEM_PROMPT`의 `price` 규칙에 중고거래 문단 하나를 더한다.
   - 뜻(`LABELING.md` 규칙 6과 같음): 중고거래 매물 화면이면 **판매자가 등록한 매물 가격**이 가격이다. 이 화면에는 정가 우선을 적용하지 않는다. 본문에 적힌 정가·구매가·새 상품 가격, 사진 속 가격, 다른 매물 가격은 가격이 아니다.
   - 중고 화면을 알아보는 단서는 일반적인 것만 쓴다(중고거래 앱 이름, 매물·채팅·관심·끌올 같은 UI 단어 등). **특정 캡처의 문구에 맞추지 않는다.** 홀드아웃의 G 2장이 그 검사다.
   - 기존 문장은 고치지 않는다. 문단 위치·영어 문체는 기존 규칙과 맞춘다.
2. `index.ts`·출력 스키마·`buildSystemPrompt`는 바꾸지 않는다. `samples/prompt-2026-10-04.ts`(고정 사본)도 그대로 둔다. 실행기 v1 변형은 `prompt.ts`를 그대로 쓰므로 실행기는 고칠 필요가 없다.
3. 검증: `deno check`(`index.ts`·`goldset-eval.ts`), 가상 fixture dry-run.

**DoD**: diff 보고 → 승인 → 커밋.
