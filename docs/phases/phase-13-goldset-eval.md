## 1. 정답 정의 (라벨 규칙) — `goldset/LABELING.md`로 고정

**가격(`price_gold`)**: 현재 제품 정책을 따른다.
- 화면의 **주 상품** 가격만 본다. 추천·목록·다른 상품 가격은 제외한다.
- 정가와 할인가가 같이 있으면 **정가**(할인 전, 보통 더 높거나 취소선이 있는 값)를 고른다.
- 가격이 하나만 있으면 그 값을 쓴다.
- **원화 금액만** 인정한다. 외화만 있으면, 원화 가격이 없으면, 주 상품을 판별할 수 없으면 **null**이다.
- 쿠폰 금액, 배송비, 적립금, 좋아요·리뷰·조회·구매 수, 사이즈, 날짜는 가격이 아니다.
- **중고거래 상세(G)는 판매자가 등록한 가격**이 정답이다. 정가 우선을 적용하지 않고, 사진 속 가격·본문의 구매가/정가·다른 매물 가격은 제외한다(2026-11-05).

**정책 대비용 보조 칸**: 정가 우선 정책 자체를 나중에 다시 판단할 수 있게 둔다.
- `price_list`: 정가(있으면)
- `price_sale`: 할인가(있으면)
- `price_foreign`: 외화 가격(있으면, `JPY 3980` 형식). 외화 처리를 바꿀 때 다시 재기 위한 기록이다(2026-11-05). 채점에는 쓰지 않는다.

**제품명(`name_keywords`)**: 이 화면 안에서 주 상품을 가려내는 핵심어 하나(여러 단어로 된 구도 된다). 부분 일치로 판정한다(띄어쓰기 무시). `|`는 이은 말이 각각 주 상품을 가려낼 수 있을 때만 쓴다(예: `브라탑|bra top`)(2026-11-06 보완). 주 상품 없이 여러 상품이 나란한 화면(가격 null인 C·D)은 어느 상품을 내도 정답으로 보고 상품마다 `|`로 잇는다. 브랜드도 같다(2026-11-06).

**원하는 제품명(`name_gold`)**: 앱의 제품명 칸에 들어가길 원하는 이름. 이번 Phase에서는 채점하지 않는다. 제품명을 다루는 Phase에서 같은 정답셋으로 다시 재기 위한 기록이며, 모델 출력을 보기 전에 적어 둔다. 채점 기준(완전 일치인지 등)은 그때 정한다(2026-11-06).

**브랜드(`brand_aliases`)**: 정답으로 인정할 표기를 `|`로 나열한다(예: `이솝|Aesop`). 하나라도 같으면 정답이다. 화면에 보이는 표기와 널리 알려진 공식 표기만 적고, 한·영을 둘 다 적을 필요는 없다(2026-11-06 보완).

**품목(`item_category`)**: 주 상품의 품목 하나. `생활용품` / `가구·인테리어` / `패션` / `뷰티` / `전자` / `기타` 중에서 고른다(2026-11-04 추가). 정답 판정에는 쓰지 않고, 결과를 품목별로 나눠 보는 데만 쓴다.

**라벨은 모델 출력을 보지 않고 붙인다.** 운영 함수의 출력(`parsed`)은 라벨링 시트에서 빼 둔다(Step 3).

## 2. 표본 설계

40~60장(최소판은 34~50장 — 맨 위 상자). 아래 유형별로 7~10장씩 모은다(최소판의 E·G는 3~5장). 실제 쓰임과 같은 맥락에서 **본인이 직접 캡처**한다. 대상은 커머스 상세 화면, 릴스·피드, 중고거래 상세다(품목 구성은 맨 위 상자). 같은 상품을 두 번 넣지 않는다. 정답셋 v1은 A·B·C·D·G 8장씩, E 4장, F 0장으로 44장이다(2026-11-05).

| 유형 | 내용 | 정답 예 |
|---|---|---|
| A | 정가·할인가 병기(주로 커머스 상세) | 정가 |
| B | 가격 하나 + 가격이 아닌 숫자 — 가격이 하나만 보이는 커머스 화면(할인 없음, 할인율+할인가만, 할인가가 화면 밖)의 쿠폰·적립·배송비·리뷰 수, 가격이 한 줄 적힌 SNS 게시물의 좋아요·공유 수 | 그 가격 |
| C | SNS 게시물 — 좋아요·조회·댓글 수만, 가격 없음 | null |
| D | 여러 상품의 가격이 섞임 — 상세+추천·광고, 큰 상품 카드+아래 목록, 같은 크기로 나란한 목록 | 주 상품 가격 또는 null |
| E | 외화 가격만(해외 몰) | null(`price_foreign`에 외화 기록) |
| F | 텍스트가 거의 없는 이미지 중심 화면 | 'OCR 부족' 판정만 기록 |
| G | 중고거래 상세(당근·번개장터 등) | 판매자가 등록한 가격 |

여러 유형에 해당하면 F > E > C > G > D > A > B 순으로 하나만 고른다(`LABELING.md` 2절). B와 D는 섞인 숫자로 가른다 — 가격이 아닌 숫자(쿠폰·배송비·좋아요 수)면 B, 다른 상품의 진짜 가격이면 D다. A·B·C는 주 상품의 원화 가격 수로 가른다 — 없으면 C, 하나면 B, 정가·할인가가 함께면 A다(SNS 게시물도 같다).

수집이 끝나면 목록을 **고정**한다(파일 목록 + 행 수). 측정을 시작한 뒤에는 정답셋을 고치거나 추가하지 않는다. 고칠 일이 생기면 다음 버전 세트로 따로 만든다.

## 3. 지표

대표 출력은 3회 실행 중 **다수결 값**(2회 이상 같은 값)으로 정한다. 다수결이 없으면 '불안정'으로 따로 센다.

| 지표 | 정의(분모) |
|---|---|
| 가격 정답 | 대표 출력 = `price_gold` (N) |
| 오추출 | 정답이 null인데 숫자를 냄 (정답 null인 장) |
| 오값 | 정답이 숫자인데 다른 숫자를 냄 (정답 숫자인 장) |
| 누락 | 정답이 숫자인데 null을 냄 (정답 숫자인 장) |
| 3회 일치 | 세 번 모두 같은 가격 (N) |
| 오답 중 저신뢰 안내 | 오답 가운데 confidence < 0.5라서 앱이 "확인 필요"를 띄운 장 (오답 수) |
| 정답 중 괜한 안내 | 정답 가운데 confidence < 0.5라서 "확인 필요"가 괜히 뜬 장 (정답 수). confidence 기준값을 조정하려면 위 지표와 이 지표를 함께 봐야 한다 |
| 기준값별 표 | 기준값 0.3·0.4·0.5·0.6·0.7마다 위 두 지표를 다시 센다. `results.csv`의 confidence로 계산하므로 API를 다시 부르지 않는다. 기준값은 바꾸지 않고 재기만 한다(바꾸는 것은 다음 Phase) |
| OCR 포함 | 정답 숫자(콤마 제거)가 `raw_text`에 들어 있음 (정답 숫자인 장) — OCR 단계 한계 분리 |
| 보조 | 제품명 핵심어 포함, 브랜드 별칭 일치 |
| 비용 | 응답 `usage`의 input/output 토큰 합계(변형별) |

모든 지표는 **유형별(A~G)** 과 **품목별(`item_category`)** 로도 나눠 보고한다.

- 다 담은 뒤 같은 쿼리에 끝 시각을 걸어 합계가 담은 장수와 같은지 확인한다. Step 3 내보내기 쿼리는 원문과 AI 결과(`parsed`)를 출력하므로 이 확인에 쓰지 않는다.
  ```sql
  -- 원문은 출력하지 않는다. 시각에는 +09(한국 시간)를 붙인다 — SQL Editor는 UTC 기준이라 빠뜨리면 9시간 어긋난다.
  -- 첫 장 확인 때는 끝 시각 조건을 빼고 돌린다. 결과의 시각도 UTC로 표시된다.
  select case when grouping(l.status) = 1 then '합계' else l.status end as status,
         count(*)                                               as n_logs,
         count(*) filter (where coalesce(l.raw_text, '') <> '') as n_with_text,
         min(char_length(l.raw_text))                           as min_len,
         min(l.created_at)                                      as first_at,
         max(l.created_at)                                      as last_at
  from public.analysis_logs l
  where l.user_id in (select user_id from ops.internal_users)
    and l.created_at >= '<수집 시작 시각>+09'
    and l.created_at <= '<수집 끝 시각>+09'
  group by rollup(l.status)
  order by grouping(l.status), l.status;
  ```
- `low_confidence`도 정상 기록이다. 정제는 됐지만 confidence가 0.5 미만이라 앱이 "확인 필요"를 띄운 경우이고, 로그에는 AI 결과가 그대로 남는다.
