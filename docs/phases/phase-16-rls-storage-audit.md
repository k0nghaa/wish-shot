# Phase 16 — RLS·Storage 정책 점검

> **이 문서 사용법**: Claude Code에 이 파일 전체를 컨텍스트로 넘기고 "**Step N을 진행해달라**"고 한 Step씩 요청한다. **사람** Step(SQL Editor 실행·대시보드 Advisor 실행·마이그레이션 적용)은 에이전트가 대신하지 않는다. 에이전트는 Step마다 보고하고 **승인을 받은 뒤 커밋**한다. 커밋 메시지에 Phase·Step 번호를 넣지 않는다.
>
> **브랜치**: 최신 `dev`에서 분기한 `chore/phase-16-rls-audit`. worktree `../wish-shot-sec`에서 Phase 15 다음에 작업한다. 점검(Step 1~3)은 15와 겹치지 않아 먼저 해도 되지만, **수정 마이그레이션(Step 4)은 15가 `dev`에 머지된 뒤** 번호(`0006` 이후)를 정한다.
>
> **공개 레포 주의(중요)**: 고치기 전의 약점 세부(어떤 정책이 어떻게 뚫리는지)는 **커밋하지 않는다**. 점검 결과는 채팅 보고와 git 제외 위치(`.omc/`)에만 둔다. 커밋은 고친 뒤에, 고친 내용과 점검 항목 수 요약만 한다.
>
> **레인 경계**: `src/**`, `supabase/functions/**` 코드는 바꾸지 않는다. 점검 중 함수·앱 쪽 문제가 나오면 보고만 하고 해당 브랜치나 후속 Phase로 넘긴다.
>
> **운영 DB 하나로 작업한다**: 마이그레이션마다 **되돌리는 SQL을 함께** 둔다.
>
> **근거 원칙**: Supabase RLS·Storage·Advisor 동작은 공식 문서로 확인한 뒤 판단한다(CLAUDE.md 규칙 6).
>
> 관련 문서: `supabase/migrations/0001~0005`, `supabase/tests/rls.sql`, `supabase/config.toml`, `CLAUDE.md`(규칙 9·11, 데이터 레이어), `docs/legal/privacy.html`.

## 목표 (Goal)

익명 로그인 도입 이후의 RLS·GRANT·함수 권한·Storage 정책이 의도대로인지 **점검표로 확인**하고, 고칠 것만 새 마이그레이션으로 고친다. 결과는 "점검 N개 중 고친 M개, 의도대로 둔 K개(사유)"로 남긴다.

## 하지 않는 것

- 앱·Edge Function 코드 수정(보고만)
- 로그인·계정 연결(Phase 22 — 보류)
- CAPTCHA 도입(후속 후보로 기록만)

## Step 1 — 점검 SQL 작성 (에이전트)

`supabase/tests/audit.sql`: 위 A~D·F 항목을 **읽기 전용 select**로 확인하는 쿼리 모음. 결과가 표로 나오게 쓰고, 각 쿼리 위에 점검 번호를 단다. 이 파일에는 판정·약점 설명을 쓰지 않는다(쿼리만 — 커밋 가능).

**DoD**: 보고 → 승인 → 커밋.

## Step 2 — 실행 (사람)

1. SQL Editor에서 `audit.sql` 실행 → 결과를 에이전트에 전달(사용자 데이터 행은 없다 — 메타데이터만).
2. 대시보드 Security Advisor·Performance Advisor 실행 → 경고 목록 전달.
3. Data API 설정의 노출 스키마 목록 확인(C1).

## Step 3 — 판정 (에이전트, 커밋하지 않음)

항목마다 **통과 / 수정 필요 / 의도대로 둠(사유)** 으로 판정해 채팅으로 보고하고 `.omc/`에 기록한다. 수정 필요 항목마다 고칠 방법과 영향(앱·기존 데이터·다른 레인)을 적는다. 사람이 고칠 목록을 승인한다.

- F2를 고치는 방법(위시 삭제 때 로그도 지움 / 보존 기간 / 방침에 고지)은 사람이 정한다. 로그를 지우는 쪽이면 **정확도 측정의 원문 내보내기(Phase 13 Step 3)가 끝난 뒤** 적용한다.
- 방침 문구 수정이 필요한 항목(F1·F2 등)은 구매처 찾기 Phase(21)의 방침 개정에 묶는다(같은 worktree에서 16 다음에 하는 OTA라 공개가 빠르다).

## Step 4 — 수정 마이그레이션 (에이전트)

1. 15가 머지된 `dev`로 rebase한 뒤 `supabase/migrations/0006_*.sql`을 쓴다(필요하면 여러 개). 새 GRANT는 명시한다(규칙 9).
2. 되돌리는 SQL을 `supabase/rollback/`에 함께 둔다.
3. `supabase/tests/rls.sql`에 고친 항목의 회귀 시험을 더한다(다른 사용자 폴더 접근 거부, `anon` 거부 등).
4. `CLAUDE.md` 데이터 레이어 서술을 바뀐 정책에 맞춘다.

**DoD**: 보고 → 승인 → 커밋. 커밋 메시지·주석에 약점 세부를 쓰지 않는다("버킷 업로드 크기·형식 제한 추가"처럼 결과만).

## Step 5 — 적용과 재점검 (사람)

1. SQL Editor에서 `0006` 적용 → `rls.sql`·`audit.sql` 재실행.
2. Advisor 재실행.
3. 앱(개발용 앱이 있으면 그쪽)에서 담기·사진 보기·삭제가 그대로 되는지 확인.

## Step 6 — 결과 기록과 PR (에이전트)

- 결과 기록: 점검 N개 중 고친 M개, 의도대로 둔 K개와 사유(약점 세부 없이), 후속 후보.
- PR을 템플릿 구조로 올린다(승인 후). PR 직전에 `dev`로 rebase.
