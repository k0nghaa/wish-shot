## 목표 (Goal)

Phase 3까지 **저장(등록)** 이 완성됐다. Phase 4는 **저장한 뒤의 관리 경험**을 채운다. 이 Phase가 끝나면: 저장한 위시의 모든 필드를 편집하고, 다른 카테고리로 옮기고, 메모·태그를 달 수 있다. 또 등록 시 **기존에 만든 카테고리 중 가장 맞는 것을 자동으로 미리 선택**해 주고, **설정 화면**에서 로그아웃·개인정보 안내를 볼 수 있다.

**이 Phase의 핵심 검증(PRD S4 탐색/관리)**: 상세 → 편집 → 필드 수정·저장 → 목록/상세 반영. 카테고리 이동(미분류 포함). 메모·태그 입력·표시. 등록 시 카테고리 자동 미리선택. 설정에서 로그아웃.

## 이 Phase에서 하지 않는 것

- **기존 v1 데이터 이관** → **안 함.** `docs/archive/migrate-sqlite-to-supabase.ts`는 보존만(실행·개조 안 함).
- **TestFlight 내부 테스트 배포** → 디자인 개편 이후로 미룸(개편 Phase에 묶음).
- **E-2 원문 clipboard 복사, 크로스-소스 중복/제품명 후보 선택 UX** → PRD 근거 없는 구현 잔가지. 개편 때 다룸(크로스-소스 중복은 PRD 비목표).
- **FR-8 범용 카테고리 분류**(내 데이터와 무관한 "셔츠→옷/여성패션") → 이후. 이 Phase는 **기존 카테고리 매칭 경량판만**.
- 이미지 자르기, 검색/정렬 옵션, URL 공유 수신, Apple 로그인, Android → 이후.

## 제약 (Constraints) — 에이전트가 지킬 것

Phase 1~3 규칙(한국어 문자열, 디자인 토큰, 비밀값 커밋 금지, 커밋 컨벤션, 문서 동기화, 데이터 레이어 경유, 모르면 묻기, 버전 임의 인상 금지)을 그대로 승계하고 다음을 추가한다.

1. **네이티브 의존성을 추가하지 않는다.** 이 Phase의 모든 기능은 JS 전용이거나 서버 측(Edge Function)이다. 네이티브가 필요해 보이면 멈추고 사람에게 묻는다(개편 Phase로 미룰 후보).
2. **편집 시 `normalized_name`을 반드시 재계산한다.** 브랜드·제품명을 바꾸면 중복 판정 키가 달라진다. 재계산은 **`src/lib/normalize.ts` 한 곳**만 쓴다(등록·중복조회와 동일 소스).
3. **편집이 중복을 만들면 차단한다.** 편집 결과 `normalized_name`이 **다른 아이템**과 겹치면 `UNIQUE(user_id, normalized_name)` 23505가 난다. 이를 잡아 "이미 같은 브랜드+제품명의 위시가 있어요"로 안내하고 저장을 막는다(자기 자신과의 일치는 정상). 등록 화면의 `DuplicateItemError`(Phase 2) 처리를 재사용하되, 편집 맥락에선 **덮어쓰기 없이 안내만** 한다.
4. **FR-8 추천은 기존 parse 호출에 얹는다.** 별도 Edge Function·별도 LLM 왕복을 만들지 않는다. `parse-screenshot-text`의 입출력만 확장한다(아래 계약). 추가 비용은 토큰 몇 개 수준.
5. **추천 카테고리는 반드시 사용자의 기존 목록 안에서만.** LLM이 목록 밖 값을 반환하면 앱이 무시한다(새 카테고리를 임의로 만들지 않는다). 추천이 없으면 지금처럼 사용자가 직접 고른다(폴백).
6. **카테고리 이름이 서버로 전송되는 것을 고지 대상에 포함한다(NFR-3 정합).** FR-8을 위해 사용자의 카테고리 이름 목록이 Edge Function/LLM으로 간다. 이는 사용자가 만든 라벨로 민감도가 낮고 이미 OCR 텍스트를 보내는 것과 같은 수준이지만, 개인정보 안내 문구가 "텍스트만 전송"과 어긋나지 않게 점검한다.
7. **데이터는 데이터 레이어(`src/lib/queries`)로만 접근한다.** 편집·이동·로그아웃 모두 쿼리 함수를 통한다. 화면에서 `supabase.from(...)` 직접 호출 금지.
8. **삭제·이동은 즉시 반영, `updated_at` 자동 갱신**(Phase 2 트리거 유지).

## FR-8 Edge Function 계약 변경 (Step 3 기준선)

`parse-screenshot-text`의 입출력을 **하위호환**으로 확장한다.

- **입력**: `{ "text": string, "categories"?: string[] }`
  - `categories`: 사용자가 이미 만든 카테고리 이름 목록. 없거나 빈 배열이면 추천을 건너뛴다(기존 동작 그대로).
- **출력**: `{ "productName": ..., "price": ..., "brand": ..., "confidence": ..., "suggestedCategory": string | null }`
  - `suggestedCategory`: **입력 `categories`에 포함된 값 중 하나**거나 `null`. 목록에 없는 값·새 이름을 지어내지 않는다(프롬프트로 강제 + 앱에서 목록 대조 검증).
  - `categories`가 비었으면 항상 `null`.
- **호환성**: `categories` 미전송 시 출력은 Phase 3와 동일(+`suggestedCategory: null`). 기존 호출부가 깨지지 않는다.
- **배포**: `npx supabase functions deploy parse-screenshot-text`(사람 실행). **앱 재빌드 무관**(서버 측).

## Step 1 — 아이템 편집 (FR-14) + 메모/태그 입력  ⭐

이 Phase의 핵심. 상세 화면에 "편집"을 붙이고, 저장한 모든 필드를 고칠 수 있게 한다.

**작업**
1. **데이터 레이어**(`src/lib/queries/items.ts`): 편집용 `updateItem`을 점검·보강한다. 입력으로 `product_name`·`brand`·`price`·`source_link`·`memo`·`tags`·`category_id`·`normalized_name`을 받아 해당 아이템을 UPDATE. `normalized_name`은 **호출부가 `normalizeName(brand, product_name)`으로 계산해 전달**한다. 23505(unique_violation)는 `DuplicateItemError`로 변환해 던진다(제약 3). (Phase 2 덮어쓰기에서 쓰던 update 경로가 있으면 재사용.)
2. **편집 화면 신설**: 상세에서 진입하는 편집 화면(라우트는 Expo Router 충돌 없는 경로로, 예: `item/[id]/edit` 또는 `item-edit/[id]` — 실제 경로는 `expo config`/타입 라우트로 검증). 기존 이미지(signed URL)를 보여주고, `제품명(필수)/브랜드/가격/링크/메모/태그/카테고리` 필드를 아이템 값으로 프리필. **OCR·분석 파이프라인은 붙이지 않는다**(이미 저장된 텍스트 편집이므로). 등록 화면(`register.tsx`)의 필드·카테고리 선택 UI를 **공통 컴포넌트로 추출해 재사용**하되, 분석 관련 로직은 제외.
3. **메모/태그**: 메모는 텍스트 입력(등록에도 이미 있음). **태그 입력 UX 신설** — 자유 입력 칩(입력 후 추가 → 칩, 칩 탭 → 제거). PRD §13 미결이므로 **자유 입력을 기본**으로 하고, 기존 태그 자동완성/선택은 선택적 개선(여력 되면). `tags text[]`에 저장.
4. **저장**: `normalizeName` 재계산 → `updateItem`. 성공 시 상세로 복귀·반영. 중복(다른 아이템과 정규화명 충돌) 시 제약 3대로 안내·차단.
5. **이미지 교체(선택)**: 여력이 되면 편집에서 이미지 교체(같은 Storage 키에 upsert, Phase 2 덮어쓰기 로직 재사용). 복잡하면 이 Phase에선 텍스트 필드만 편집하고 이미지 교체는 결과 기록에 "미포함"으로 남긴다.
6. 커밋: `feat: 아이템 편집 화면 (FR-14) + 메모/태그 입력`

**DoD**
- [ ] (사람) 상세 → 편집 → 제품명/브랜드/가격/링크/메모 수정·저장 → 상세·목록에 반영
- [ ] (사람) 태그 입력·삭제 → 상세에 칩으로 표시
- [ ] 브랜드/제품명 변경 시 `normalized_name` 재계산(단일 소스). 다른 아이템과 겹치게 편집하면 저장 차단·안내
- [ ] 편집 화면은 OCR/분석을 실행하지 않음. 디자인 토큰만·문자열 한국어. `tsc --noEmit` 통과

## Step 3 — 경량 카테고리 자동 추천 (FR-8)

기존 parse 호출에 얹어 **추가 비용·재빌드 없이** 등록 시 카테고리를 미리 선택해 준다.

**작업**
1. **Edge Function 확장**(위 계약): `parse-screenshot-text`가 `categories`를 받아 `suggestedCategory`(목록 내 값 또는 null)를 반환. 프롬프트에 "반드시 주어진 목록 중에서만 고르고, 맞는 게 없으면 null"을 명시. 하위호환 유지. 재배포(사람).
2. **`parse` 쿼리**(`src/lib/queries/parse.ts`): 호출 시 `listCategories()`의 이름 목록을 함께 전송, 응답의 `suggestedCategory`를 반환값에 포함. **목록에 없는 값은 무시**(제약 5).
3. **`useAnalysis`**: 정제 결과에 `suggestedCategory`를 실어 화면에 전달.
4. **등록 화면(`register.tsx`)**: `filled` 시 `suggestedCategory`가 있으면 **해당 카테고리를 미리 선택**하고 작은 "추천" 힌트를 표시. 사용자가 다른 카테고리를 고르면 그대로 덮인다(강제 아님). 추천이 없으면 지금처럼 미선택.
5. `analysis_logs.parsed`에 `suggestedCategory`도 남는지 확인(추천 정확도 평가용, 스키마 변경 없이 jsonb에 포함).
6. 커밋: `feat: 경량 카테고리 자동 추천 (FR-8, 기존 카테고리 매칭)`

**DoD**
- [ ] 함수 재배포됨. `categories` 미전송 시 기존과 동일 응답(+`suggestedCategory: null`)
- [ ] (사람) 기존 카테고리와 맞는 스크린샷 등록 시 해당 카테고리가 미리 선택됨. 안 맞으면 미선택
- [ ] 목록 밖 추천값은 앱이 무시(임의 카테고리 생성 안 함)
- [ ] `tsc --noEmit` 통과

## 미결 사항 (진행 중 결정, 결과 기록에 남길 것)

- **편집 화면 형태**: 별도 화면 vs 상세 인라인 편집. 라우트 경로(Expo Router `[id].tsx`와 `[id]/` 공존 여부) 확정.
- **태그 입력 UX**(PRD §13 미결): 자유 입력 기본. 기존 태그 자동완성/선택 추가 여부.
- **이미지 교체 포함 여부**: 텍스트 필드만 vs 이미지까지. 복잡도 보고 결정.
- **중복 편집 정책**: 다른 아이템과 정규화명 충돌 시 "차단·안내"로 확정(덮어쓰기 제공 안 함) — 실사용 후 추가 UX 필요하면 보강.
- **FR-8 추천 힌트 UI**: 미리선택만 vs "추천" 배지까지. `confidence`와 연동할지.
- **설정 진입점 위치**: 홈 헤더 아이콘 vs 별도 탭.

**이 문서에서 확정한 결정:**
- 범위 = 편집(FR-14)·카테고리 이동(FR-15)·메모/태그 + FR-8 경량 추천 + 설정 화면. **재빌드 없음.**
- **v1 데이터 이관: 범위에서 제외**(archive 보존만).
- **FR-8은 경량판만**(기존 카테고리 매칭, parse 호출에 얹음). 범용 분류·별도 호출 없음.
- 편집이 중복을 만들면 **차단·안내**(덮어쓰기 없음).
- 이미지 교체는 **선택**(코어는 텍스트 필드 편집), 태그 입력은 **자유 입력 칩** 기본.
- TestFlight·clipboard·크로스소스 중복은 **개편 이후**.
- PRD 갱신은 **사람 확인 후 에이전트가 노션 직접 수정**(Step 5).
